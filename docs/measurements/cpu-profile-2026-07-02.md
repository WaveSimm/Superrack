## 병렬 워커 풀(BACKLOG A2) 도입 시 예상 — i5-9400F (6C/6T, HT·E코어 없음)

부하가 채널 수에 선형(전 run 일치) = 채널 독립 병렬화의 이상적 조건. 오디오 스레드 + 워커 4 = **5개 처리 레인**(1코어는 GUI/Writer/OS 몫), 실효 ~4× 가정:

| 구성 | 현재(직렬) | 병렬 예상 | 근거 |
|---|---:|---:|---|
| Pro-Q3→Pro-R @48k/256 | 16ch | **32ch 여유** | 32ch 직렬 avg 118%→레인당 ~24%, pk ~31% |
| Pro-Q3→Pro-R @96k/96 | 4ch | **16~24ch** | 24ch 직렬 avg 347%→레인당 ~70%, pk ~88% (경계) |
| Pro-Q3→Pro-L2 @96k/96 | 4ch | ~16ch (경계) | peak 지배형이라 레인당 스파이크 여유 필요 |
| EQ류 | 32ch | 32ch (변화 없음) | 이미 여유 |

주의점:
- **1ms 예산에서 fork-join 오버헤드(웨이크+조인 ~수십 µs)가 수 %** — spin→semaphore 전략 필수(리서치 §3).
- peak 스파이크는 같은 플러그인이면 채널 간 **상관**될 수 있어(모두 같은 블록에서 비쌈) 병렬화해도 peak/avg 비는 유지됨 — peak 지배형 플러그인은 96k에서 버퍼 128~192 권장.
- 32ch@96k/96 + 무거운 체인 풀랙은 이 CPU(2018년 6코어)로는 병렬화해도 빠듯 — 코어 많은 CPU로 가면 선형으로 더 늘어남.

## 분석

- **PLAN §3 리스크 실증**: "단일 오디오 스레드 — 32채널 × 체인은 CPU 1순위 리스크"가 수치로 확인됨. Pro-R급 무거운 플러그인은 전 채널 배치 불가.
- **부하는 채널 수에 선형**(Run 2: 2→4→8ch에서 avg 10.4→31.0→83.8%). 페이즈당 고정 오버헤드보다 플러그인 처리량이 지배적 → **버퍼 상향만으로는 avg 부하가 거의 안 내려감**(처리량 비례). 버퍼 상향은 peak 지터 흡수에만 유효.
- 실전 수용 전략:
  1. 무거운 공간계(리버브 등)는 소수 채널에만 인서트 (채널별 체인 차등 구성 — 이미 지원)
  2. SR 48kHz 운용 시 처리량 절반 → 같은 체인으로 약 2배 채널 기대
  3. (신규 백로그 후보) **채널 병렬 처리**: 채널이 완전 독립(1:1, 합산 없음)이므로 워커 스레드 풀로 채널 분할 병렬화 가능 — 이론상 코어 수 배 확장. 오디오 콜백 내 fork-join 설계 필요(락프리 배리어).
- **주의**: 합성 부하는 플러그인 처리만 재현 — 실제 32ch 드라이버의 채널 I/O 오버헤드 미포함. 다채널 실기 확보 시 재검증.
